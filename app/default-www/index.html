Your website, locally presented

Welcome to
Pseudo-Chrome.

Present a prepared website in a familiar browser-style window. Pseudo-Chrome supplies Chromium rendering and starts the local hosting processes for you.

03 / KEEP LOCAL

Your own workspace

Website files live in www, separate from the application installation and its bundled runtimes.

This manual is a website too.

It uses only its own local HTML, CSS, JavaScript, and icon. It contains no external fonts, libraries, media downloads, or backend dependencies. Search, chapter navigation, copying examples, and printing work locally.

Your default website

This manual is bundled with Pseudo-Chrome 1.0.0. The app copies it into www only when that directory is empty and no site.json exists. Existing website files and existing site configuration are left untouched. Updating the application does not replace a website you already configured.

Pseudo-Chrome is an independent utility. It is not Google Chrome and does not provide Chrome accounts, synchronization, or extensions.

Start here / Windows

Get your website on screen.

Keep the application package intact, then put your prepared website in its own folder.

  1. Extract the complete application

    Extract the Windows portable ZIP into a folder and run Pseudo-Chrome.exe. Keep resources and the other bundled files beside the executable. Do not run it from inside the ZIP. A fresh, unconfigured installation opens this manual.

  2. Open your website folder

    Choose ⋮ → Settings → Website → Open folder. On Windows, this opens %AppData%\Pseudo-Chrome\www. The default manual is stored here until you replace it with your own website.

  3. Replace the website contents

    Close Pseudo-Chrome and back up the current website and site.json. Replace the contents of www with the prepared project. If a package contains a www folder, copy that folder’s contents, so the website files sit directly in the app’s www. Remove the old manual files from the active website rather than merging the projects.

  4. Choose the host and restart

    Reopen the app. In Website settings, choose a website type if automatic detection is not suitable. Set the document root and application entry where required. Use Save and restart, or Restart website if the settings are already correct. Set the start page to / unless your project needs another local path.

Restore this manual when you need it

Close the app and back up the active website and configuration. In the extracted Windows application, the bundled manual is in resources/app/app/default-www. Copy that directory’s contents into www. Select Static / built frontend, set Document root to ., clear any old application entry or npm script, and leave SPA routing off. Set the start page to /.

site.json — manual
{
  "mode": "static",
  "documentRoot": ".",

  "spa": false

If applying the configuration above directly, create or update site.json in the parent configuration folder, beside www, while Pseudo-Chrome is closed. Copy the complete example shown here; no separate configuration download is required. It is not a website file.

Linux

Extract the Linux TAR.GZ and run ./pseudo-chrome as a regular user. On Debian/Ubuntu, install the DEB with the system package manager, then open Pseudo-Chrome from the application menu. The website setup is the same; the normal website folder is ~/.config/Pseudo-Chrome/www.

Switching websites safely

  1. Close Pseudo-Chrome so the website processes stop.
  2. Back up the current www and, if useful, its site.json.
  3. Replace the website files and apply the matching configuration.
  4. Open Pseudo-Chrome and check the Website settings status and log.

Changing sites at the same local origin may reuse cookies and browser storage. Clear website data when you need an independent demonstration.

Automatic detection

With the default layout, detection checks root index.html, then index.php or public/index.php, built dist/index.html or build/index.html, and a Node package start/main entry or server.js. If multiple possible entry points exist, select an explicit type and entry to avoid choosing the wrong one.

Node and native server contract

The launcher supplies a local HOST and PORT. The server must use them, or equivalent supported arguments, and listen on 127.0.0.1. A backend that binds all network interfaces is rejected. An explicit entry takes precedence over an npm script.

What the bundled host provides

nginx fronts the local website. Supported request behavior includes ordinary HTTP methods and bodies, cookies, redirects, uploads, static byte ranges and conditional requests, streaming, and WebSocket upgrades. PHP uses FastCGI and supports front-controller routes, sessions, uploads, and PATH_INFO.

Project infrastructure still matters.

The app does not compile source, build frontend projects, install dependencies automatically, provision databases or queues, or interpret arbitrary nginx/Apache configuration and .htaccess. A project that depends on those features needs its own preparation or adaptation.

A project with several backend services must provide its own startup and coordination arrangement. Selecting a host type alone does not automatically combine multiple unrelated backends.

Website reference

Configure the project.

Use ⋮ → Settings → Website. The same values are stored in site.json beside www.

Use Save and restart after changing the form. If you edit site.json directly, close the application first. JSON requires double quotes and does not accept comments or trailing commas.

The examples below are complete configuration snippets to copy and adapt. Paths such as dist, server.cjs, public/index.php, and bin/server.exe refer to files in your prepared website. A configuration example does not create those files or compile a backend.

config.pseudochrome

This optional UTF-8 file belongs directly in www. It uses one KEY=VALUE per line. Blank lines and whole-line comments beginning with # or ; are allowed; values may be quoted. Key names are case-sensitive. Use only SIMULATED_DOMAINNAME and PORT; the file may be up to 16 KiB. Unknown or repeated keys and invalid values produce a startup error.

www/config.pseudochrome
# Displayed address, without a scheme, path, credentials, or port
SIMULATED_DOMAINNAME=demo.example
# Actual listening port; 0 means automatic
PORT=43881

PORT overrides the public port from site.json while present. Omit it to use Website settings. An occupied fixed port gives an error. Restart the website after edits. Even when the document root is public or dist, keep this file directly in www. The host does not serve it as website content.

SIMULATED_DOMAINNAME changes the displayed hostname while preserving the path, query, and fragment. It is an address-bar alias: the website still uses its real local origin. It does not change DNS, add HTTPS, or rewrite domain-bound cookies, JavaScript origins, or OAuth rules. An empty value disables the alias. Connection details show the actual origin.

The settings screen shows the startup timeout in seconds. It accepts 1–180 seconds, matching the backend limit. The JSON field stores the equivalent value in milliseconds.

Do not include secret values when sharing configuration or a test report. A framework may also use its own environment files; Pseudo-Chrome does not interpret every framework’s setup automatically.

Page titles and icons

Tabs follow the website’s <title> and favicon, including changes made by JavaScript during navigation. The native window title follows the active tab. Supply a normal <link rel="icon" href="/favicon.svg">, PNG, or ICO asset; the app also checks /favicon.ico. Missing or unsupported icons use a fallback. The manual uses the app’s own SVG icon, including after reload. The simulated hostname changes the displayed address, not your page title.

Tab search and menus

The top-left arrow opens Search tabs. Filter open tabs by title or address, choose a result to switch to it, or use its close button. The list contains only currently open tabs.

The ⋮ menu contains inline SVG zoom controls, full screen, printing, website actions, Settings, and About. Its actions are directly in the menu, without a Website submenu. The menu, tab search, and profile popup stay inside the application window and scroll internally when needed. Press Esc or click outside a popup to close it.

The website right-click menu offers applicable editing commands, link copying, opening local links in a new tab, navigation, reload, and Inspect.

Developer tools and Inspect

Choose ⋮ → Developer tools, press F12, or press Ctrl + Shift + I to open DevTools for the active website tab. Use its Console, Elements, Sources, and Network panels to examine your website. In DevTools, open ⋮ → Dock side and choose the right, left, bottom, or separate-window icon. You can dock it again after moving it out; reopening DevTools uses its last dock position. Right-click an element on the website and choose Inspect to select that element in the Elements panel for the clicked tab.

From Settings or About, Developer tools switches to the last website tab, or another remaining website tab if that tab was closed, so its docked inspector is visible. With no website tab open, the menu action is disabled and the shortcuts do nothing. Closing DevTools leaves the website open; closing its website tab also closes that inspector.

External resources versus external pages

A local page can request internet images, fonts, scripts, APIs, and embedded frames. Opening an external address as a top-level page is blocked, including external redirects and new-window links. Normal Chromium rules, including CORS and mixed-content checks, still apply.

This manual’s chapter links stay on the current page. Its search shortcut is /; this is a manual feature, not an application-wide shortcut.

Settings open inside the same browser-style shell.

Appearance

Choose System, Light, or Dark, and adjust page zoom. System follows the operating system’s appearance. A website keeps its own CSS; this manual follows the browser’s preferred color scheme, so it responds to the app’s appearance selection.

Under Profile picture, choose Default, Spaceship, Swept hair, Blue shirt, or Alpine castle. The selected picture appears in the toolbar and is saved in the app settings. Click the toolbar picture to open the local profile popup, then choose Customize profile or Appearance. The popup also provides Website settings and Open www folder. Under Profile name, enter a name of 1–64 characters and choose Save or press Enter. Leading and trailing spaces are removed; an empty name is rejected. The saved name appears in the main menu, profile popup, and toolbar tooltip. These preferences stay on this computer; they do not create another browser-data profile or connect an online account.

Website

Open www, inspect the current server status, choose a host type, configure the project, and save/restart. Expand Server log to read recent messages, copy the log, or open the configuration folder.

Allow other apps on this computer to access the website is off by default. Turn it on to use the public local address in another browser or client. The switch applies immediately, and both modes remain bound to 127.0.0.1; it does not open LAN access. Server-side calls to the public local address also count as external requests. This restricts the app’s gateway, not separately exposed custom backend ports or processes with access to your OS account.

Startup and display scaling

The startup window follows the selected light or dark theme, using the custom app icon and subtle bottom-edge colors. It reports real preparation and website-startup status. It is fixed at 693 × 349 device-independent pixels, about 866 × 436 physical pixels at 125% scaling. Its size does not stretch with the main window.

The normal main window starts at 976 × 722 device-independent pixels, with a minimum of 680 × 540. Its tab strip and toolbar total 86 device-independent pixels, about 108 physical pixels at 125%. Resizing changes the available website viewport.

Use the app’s controls for app settings.

A normal website, including this manual, has no access to the privileged application bridge. The menu paths above are instructions rather than links that change settings automatically.

Browser storage and local identity

Keep or reset saved data.

The browser profile is persistent. Website files and browser data are separate. Local storage, IndexedDB, Cache Storage, the origin-private file system (OPFS), and service workers use the real local origin. Cookies follow the real host/domain, path, expiry, SameSite, and Secure rules; they are not scoped by port. Session storage belongs to a tab, survives reload, and ends when the tab closes.

The local origin

A website origin includes its protocol, host, and port. Pseudo-Chrome normally reuses an available saved port, such as http://127.0.0.1:43881, so origin-based storage can survive an application restart. Use the actual address shown in connection details; the example port is not a fixed requirement. A simulated hostname does not create another origin.

In automatic port mode, if another process occupies that port, the app may choose another one. A fixed PORT in config.pseudochrome instead reports a startup error. Chromium then sees a different origin, so origin-scoped storage may appear to be missing. A port change alone does not isolate cookies. The previous browser data may still exist under the earlier origin.

What may persist

  • Cookies under their normal domain/path/expiry rules, plus local storage, IndexedDB, Cache Storage, OPFS, and service worker registrations under their origin and lifetime rules.
  • Backend data your own project writes, such as a SQLite database, upload, or application file.
  • PHP sessions and temporary files managed by the bundled host under the application’s configuration directory.

Storage durability

A website can call navigator.storage.persist() to request persistent storage. The app asks for Allow or Block, and the permission appears in site controls after that request. This asks Chromium to protect eligible data from routine eviction; it does not promise unlimited disk space, a backup, or protection from Clear website data. Normal storage APIs work without this extra grant, subject to Chromium’s quotas and cookie rules. Cookies bound to a public domain are not rewritten for the local site.

Clear browser data

Choose ⋮ → Clear website data…, then confirm. This removes the demonstration profile’s browser storage and cache. Files inside www are not removed. A project’s database or saved files need their own reset procedure.

Switching websites at the same origin reuses that origin.

For a clean demonstration, clear browser data when replacing one website with another. This also avoids an old service worker or cache affecting the next site. Back up any browser data you need before clearing it.

Restarting the website restarts its backend processes. Reloading a tab reloads the page. Neither action by itself is a “delete my data” command.

Website interactions

Permissions, uploads,
downloads, and print.

Use ordinary website interactions within the local demonstration.

Permission requests

Supported local-site requests open a popup beneath the address bar for microphone, camera, geolocation, notifications, clipboard reading, pointer lock, keyboard lock, or persistent storage. The address bar shows which access is being requested. Camera and microphone prompts offer Allow while visiting the site, Allow this time, and Never allow. Other supported requests offer Allow or Block. Closing the popup or pressing Escape dismisses that request without saving a block.

Allow this time lasts for the requesting page until navigation or closure. Allow while visiting the site lasts while local website tabs remain open, or until the app exits. Allow, Block, and Never allow are saved for that exact origin in permissions.json, beside www. Microphone and camera choices are separate. Unsupported permissions and requests from external origins are blocked.

Address-bar site controls

Click the tune icon at the left of the address to see the local connection and only the permissions this origin has actually requested. Checking a permission’s status alone does not add it to this list. Use a permission switch to allow or block it, or choose Reset permissions to ask again. Revoking or resetting access reloads open tabs for that origin so existing access stops. Saved permission choices remain separate from cookies and cache; reset them when replacing a website at the same origin. The local HTTP connection is identified as local and is not presented as an HTTPS connection.

A browser API’s presence does not guarantee available hardware, operating-system permission, or a working external service. Test those features on the Windows machine used for the presentation.

Live camera and microphone previews

When a website requests camera or microphone access, its media permission popup automatically shows a live preview for the requested device types while you decide. The camera image is real, and the microphone input-level meter measures sound without playing it back. Use Preview camera and Preview microphone to choose the preview devices; this does not override the website’s device selection. The preview does not grant the website access. Closing or answering the prompt, switching tabs, navigation, and leaving the application stop the preview tracks. An unavailable device or denied OS permission shows an error instead of simulated media. This manual does not request camera or microphone access.

Choose and upload files

A website can show its normal file picker or accept dropped files. The website determines which files it accepts and what happens to uploaded data. A multipart PHP upload and a JavaScript fetch upload can exercise different request paths.

Save downloads

Website downloads open a save dialog. Choose the destination and filename, or cancel. The demonstration site does not choose an arbitrary save location silently.

Print

Use ⋮ → Print… or Ctrl + P to print the current website. The Print manual button at the top of this page prints all chapters, including chapters hidden by navigation or search. Printer and PDF options depend on the operating system.

Current hosting limits

The bundled PHP configuration allows POST bodies and individual uploads up to 64 MiB, a 256 MiB memory limit, and 120-second input/execution limits. Its gateway buffers chunked PHP POST/PUT/PATCH bodies without a Content-Length up to 16 MiB. nginx accepts bodies up to 256 MiB; backend proxy and PHP connections have 120-second timeouts. A website can impose smaller limits.

Use website projects you trust.

The renderer is isolated from Electron and Node APIs. A hosted backend still runs with your user account’s file and network permissions; it is not a container.

Find the cause

When something needs attention.

Start with ⋮ → Settings → Website → Server log. The selected host, entry, and document root determine how the website starts.

“Website needs attention”

Check that the entry exists, dependencies are present, the selected mode matches the project, and the backend binds the provided local HOST and PORT. Read the first useful error in the log, fix the cause, then restart.

The page is blank or a file is missing

Check the document root and the browser’s developer-tools Console and Network panels. Ensure that only the contents of the intended website were copied, without an unintended extra directory level. The actual public directory must contain its page and assets.

React routes fail after reload

Enable SPA routing for a static build with extensionless routes. An SSR project instead needs its prepared Node server and deployment dependencies. A development source tree is not the same as a built site.

My PHP project does not work

Set the public directory and front controller correctly. Include vendor dependencies and project configuration. Check required PHP extensions and database services. Apache rewrites and .htaccess directives are not imported automatically.

A native server will not start

Use a Windows x64 executable on Windows, compiled before copying it into www. Include required DLLs or other runtime files. The launcher does not compile Rust or C++ source. Check binding and startup arguments in the log.

A remote image, API, or login fails

Check internet access, credentials, CORS, domain and HTTPS requirements, mixed-content policy, and the remote service. External top-level navigation is intentionally blocked. A website that requires an external login redirect may need a demo-specific flow.

Cookies or saved state seem missing

For origin-scoped data such as local storage or IndexedDB, check whether the local port changed. For cookies, check their host/domain, path, expiry, SameSite, and Secure attributes; a port change alone does not separate them. Closing the app normally preserves the browser profile, but session-scoped data follows its own lifetime rules.

Changes do not appear

Reload a static page; use Ctrl + Shift + R to bypass its HTTP cache. Restart after backend or hosting-configuration changes. Clear website data when an old service worker or stored state is the cause.

Configuration will not save

Arguments must be a JSON array of strings; environment variables must be an object of string values. Paths must remain inside www. Use 1–180 seconds for the settings screen’s startup timeout. If editing a JSON file manually, close the app and preserve a backup first.

The interface looks different from Chrome

The interface uses a Chrome-style layout, but OS fonts, scaling, rendering, and Chromium versions affect exact appearance. This is a website demonstration utility with a restricted navigation model; it does not reproduce every Chrome service or feature.

Platforms

The supplied builds target Windows 10/11 x64 and x86-64 glibc Linux. Linux requires glibc 2.28 or newer and Electron’s usual desktop libraries. The DEB declares those dependencies; the portable TAR relies on the host’s supported user-namespace sandbox. Run the app as a regular user.

The Windows package includes official x86 nginx through Windows x64 WOW64 support; the app, Node.js, PHP, and backend process supervisor are x64. ARM, macOS, and Alpine/musl builds are not included. The Windows executable is unsigned.

What remains different from a public website

A local HTTP origin differs from a public HTTPS domain. Domain-bound cookies, authentication callbacks, CORS, certificates, DRM, extensions, and Google-specific services may behave differently. Databases, queues, credentials, extra services, and custom native/PHP dependencies remain project requirements.
